# Logos

Единое рабочее место менеджера для переписки с клиентами через подключённые мессенджеры.

## Состояние проекта

Реализованы бэкенд и SPA: приглашения менеджеров, профиль, Telegram, общая переписка, теги, сортировка и сохранённые фильтры.

Правки [#10](https://github.com/ashenoooone/logos/issues/10): менеджеры входят по одноразовому email-коду; администратор — по прежнему логину и паролю. Входящие скрывают служебный `/start`, сохраняют автора ответа и поддерживают поиск по всей истории с кириллицей. Решения — [ADR-0008](docs/adr/0008-demo-feedback-and-manager-otp.md), фактический API — [контракт](docs/backend-contract.md).

Перед запуском обновлённого приложения примените миграции: `uv run alembic upgrade head`. Миграция `0010` удаляет только служебные команды запуска из истории и добавляет авторство сообщений и OTP.

**Ручная приёмка продуктовых экранов не подтверждена.** Подтверждение пользователя от 2026-11-04 относится только к техническому фронтенду — [хендофф](docs/frontend-handoff.md). Получение писем в локальном Mailpit не доказывает внешнюю доставку менеджеру.

Проверены все 8 открытых [GitHub issues](https://github.com/ashenoooone/logos/issues) и подготовлены их локальные копии. Дата снимка и соответствие файлов — в [индексе историй](docs/stories/README.md).

## Принятые решения

- **Бэкенд:** Python 3.13, uv, FastAPI, Uvicorn; синхронный SQLAlchemy 2, Alembic; argon2-cffi (Argon2id).
- **Проверки бэкенда:** pytest, Ruff, mypy.
- **Клиент:** React + Mantine UI, TypeScript + Vite, pnpm, TanStack Router с маршрутами в коде; ESLint, Vitest + Testing Library.
- **Структура фронтенда:** FEOD (базовый вариант), профиль `frontend/feod.profile.md`; границы слоёв и публичное API модулей проверяются в `pnpm lint`.
- **База данных:** SQLite, файл, путь задаётся окружением.
- **Границы:** одна установка для одной компании.
- **Первая интеграция:** Telegram Bot API, бот по токену.
- **Первый администратор:** закрытая команда развёртывания, без публичной регистрации.

Источники и последствия: [ADR-0001](docs/adr/0001-project-baseline.md) (границы продукта), [ADR-0002](docs/adr/0002-backend-initialization.md) (инструменты бэкенда и первый администратор), [ADR-0003](docs/adr/0003-frontend-tooling.md) (pnpm и TanStack Router), [ADR-0004](docs/adr/0004-frontend-initialization.md) (сборка, проверки и подключение фронтенда), [ADR-0005](docs/adr/0005-frontend-feod.md) (FEOD-структура и проверка границ). Реализованный HTTP-контракт — в [docs/backend-contract.md](docs/backend-contract.md).

## Установка и запуск

Требуются Python 3.13 и [uv](https://docs.astral.sh/uv/). Команды бэкенда в этом разделе выполняются из корня репозитория: относительный путь к SQLite и `alembic.ini` считаются от текущего каталога.

```sh
# если Python 3.13 ещё не установлен
uv python install 3.13

# окружение и зависимости строго по uv.lock
uv sync --locked
```

### Конфигурация

Основная настройка — путь к файлу SQLite:

```sh
cp .env.example .env
```

Переменные окружения бэкенда:

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `LOGOS_DATABASE_PATH` | путь к файлу SQLite | `data/logos.sqlite3` |
| `LOGOS_ALLOWED_ORIGINS` | дополнительные разрешённые Origin через запятую | только same-origin |
| `LOGOS_PUBLIC_BASE_URL` | базовый адрес фронтенда для ссылок в письмах | `http://localhost:5173` |
| `LOGOS_SMTP_HOST` | SMTP-сервер | `127.0.0.1` |
| `LOGOS_SMTP_PORT` | SMTP-порт | `1026` |
| `LOGOS_SMTP_FROM` | адрес отправителя | `no-reply@logos.local` |
| `LOGOS_SMTP_TIMEOUT` | таймаут SMTP-соединения, секунды | `10` |
| `LOGOS_SMTP_USERNAME` | имя пользователя SMTP, если требуется | не задано |
| `LOGOS_SMTP_PASSWORD` | пароль SMTP, если требуется | не задан |
| `LOGOS_SMTP_TLS` | `none`, `starttls` или `ssl` | `none` |

`LOGOS_ALLOWED_ORIGINS` — это только список Origin, которым разрешены изменяющие запросы с CSRF; CORS бэкенд не настраивает, а на атрибут `Secure` cookie эта переменная не влияет. `Secure` выставляется по фактической схеме запроса. Если TLS завершается на reverse proxy, Uvicorn запускается с явным доверием к заголовкам прокси, иначе схема останется `http`:

```sh
uv run uvicorn logos_backend.app:app --host 127.0.0.1 --port 8000 --workers 1 \
  --proxy-headers --forwarded-allow-ips 127.0.0.1
```

`--forwarded-allow-ips` должен содержать только адрес доверенного прокси, не `*`.

Всё сразу в Docker (mailpit + backend + frontend на nginx): `scripts/up.sh` — собирает образы, применяет миграции (с тестовым админом `admin`/`admin`, отключить `LOGOS_DEV_ADMIN=0`), поднимает на `http://localhost:8080`, Mailpit на `http://localhost:8026`. База и вложения в volume `logos-data`. Остановить: `docker compose down`.

Разработка с hot reload: `scripts/dev.sh` — mailpit в Docker, `uv sync`, миграции (тот же тестовый админ), `pnpm install`, затем uvicorn `--reload` на `127.0.0.1:8000` и Vite на `http://localhost:5173`. Ctrl+C останавливает оба. База — локальная `data/logos.sqlite3`, не volume.

Для локального перехвата писем используется Mailpit из `docker-compose.yml`. Порты опубликованы только на loopback и не совпадают с портами remo-site:

```sh
docker compose up -d mailpit
```

- SMTP: `127.0.0.1:1026`
- веб-интерфейс: `http://127.0.0.1:8026`

Бэкенд отправляет через SMTP приглашения, коды входа и подтверждения смены email. Mailpit перехватывает письма локально; внешнюю доставку это не подтверждает. Очереди и фоновых повторов нет. При сбое приглашения возвращается `502`, ожидающий менеджер сохраняется для повтора. Запрос кода возвращает общий `503` при ошибке SMTP; письмо одинакового формата отправляется на любой корректный email, но войти может только активированный менеджер. Код действует 10 минут, допускает 5 попыток, повторная отправка — через 60 секунд. Приглашение содержит `/invitation#token=...`; восстановление пароля менеджера удалено.

Приложение **не загружает `.env` автоматически**. Значение нужно явно экспортировать в окружение процесса:

```sh
set -a
. ./.env
set +a
```

Без переменной `LOGOS_DATABASE_PATH` используется `data/logos.sqlite3` относительно текущего каталога. Для развёртывания безопаснее задать абсолютный путь, не зависящий от каталога запуска:

```sh
export LOGOS_DATABASE_PATH=/var/lib/logos/logos.sqlite3
```

Пустой или состоящий из пробелов `LOGOS_DATABASE_PATH` считается неустановленным. Каталог и файл SQLite игнорируются git: это рабочие данные установки, их не коммитят.

### Миграции

Схема создаётся и обновляется только явной командой; сервис не применяет миграции при старте:

```sh
uv run alembic upgrade head
```

Команда создаёт отсутствующие родительские каталоги файла БД.

### Запуск сервиса

Начальный запуск — один процесс, привязанный к loopback:

```sh
uv run uvicorn logos_backend.app:app --host 127.0.0.1 --port 8000 --workers 1
```

Проверка готовности: `curl http://127.0.0.1:8000/health` → `200 {"status":"ok"}` после применённых миграций, иначе `503 {"detail":"Database is not ready"}`. Точный контракт — в [docs/backend-contract.md](docs/backend-contract.md).

Многопроцессную схему не настраивать: SQLite рассчитан на одного писателя, а фоновый опрос Telegram (`getUpdates`) должен идти ровно в одном процессе.

Бэкенду нужен исходящий HTTPS к `api.telegram.org`. Python с python.org на macOS по умолчанию не видит системные корневые сертификаты, и запросы к Bot API падают с `CERTIFICATE_VERIFY_FAILED` (бэкенд отвечает `502`). Решение — один раз выполнить `/Applications/Python 3.13/Install Certificates.command` или задать `SSL_CERT_FILE` с файлом корневых сертификатов.

### Создание первого администратора

```sh
uv run logos-backend create-admin --login root
```

- Команда требует интерактивный терминал. Пароль вводится скрыто дважды; он не принимается аргументом, переменной окружения и не имеет значения по умолчанию или требований сложности. Пустой пароль и несовпадение повторов отклоняются.
- При запуске без TTY команда завершается ошибкой, не запрашивая пароль. Если терминал не позволяет отключить эхо при вводе, команда также завершается ошибкой, не читая пароль.
- Логин обязателен, не может быть пустым или состоять только из пробелов и сохраняется без нормализации. Других полей учётной записи нет.
- Если администратор уже существует, команда завершается с ненулевым кодом и не меняет ни логин, ни хеш — независимо от переданного логина. Пароль при этом всё равно запрашивается до обращения к БД; авторитетной является вставка в БД.
- Сохраняется только Argon2id-хеш.
- Коды завершения: `0` — создан; `1` — администратор уже есть, БД не готова, ошибка ввода, хеширования или хранения пароля/записи; `2` — неверные аргументы, включая пустой логин.

Команда не создаёт публичной регистрации. Созданный администратор входит через `POST /auth/admin/login` с тем же логином и паролем; контракт входа — в [docs/backend-contract.md](docs/backend-contract.md). Если `create-admin` сообщает о неготовой БД, сначала выполните `uv run alembic upgrade head`.

### Демо-данные

`scripts/dev.sh` и `scripts/up.sh` по умолчанию заполняют пустую базу фейковыми данными (миграция `0009`, `LOGOS_DEMO_SEED=1`): менеджеры `anna@demo.logos`, `igor@demo.logos`, `maria@demo.logos`, теги, диалоги и демо-бот, если задан `LOGOS_DEMO_BOT_TOKEN` (токен только из окружения, в репозитории его нет). Вход менеджера — по коду из Mailpit; пароль `demo1234` нужен только для изменения пароля в профиле. Отключить заполнение: `LOGOS_DEMO_SEED=0`. Уже заполненная база не меняется — для демо начните с новой.

## Фронтенд

Требуются Node.js **24.15.0** (маркер `frontend/.nvmrc`; поддерживаемый диапазон `>=24.15.0 <25`) и pnpm **11.25.0**. Активируйте Node.js до установки и запуска: `node --version` и `pnpm --version` должны соответствовать этим требованиям. Случайный Node.js 20 из другого каталога в `PATH` не поддерживается. Точные зависимости — в `frontend/package.json` и единственном `frontend/pnpm-lock.yaml`; workspace нет.

Все следующие команды выполняются из `frontend/`:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Dev-сервер по умолчанию доступен на `http://localhost:5173`. Бэкенд запускается отдельно из корня по инструкции выше на `127.0.0.1:8000`, после явного применения миграций.

Главная после входа — рабочий хаб роли. `/login` — вход менеджера по коду, `/login/admin` — администратора по логину и паролю. Приглашение открывается на `/invitation#token=...`; восстановление пароля менеджера больше не используется.

Vite проксирует `/health`, `/auth`, `/admin`, `/invitations`, `/account`, `/conversations`, `/messages`, `/tags` в dev и preview. Бэкенд запускать с `LOGOS_ALLOWED_ORIGINS=http://localhost:5173`, фронтенд открывать по `localhost`, не `127.0.0.1`. CORS бэкенда не менялся.

### Проверки и локальная сборка

```sh
pnpm lint
pnpm type-check
pnpm test
pnpm build
pnpm preview
```

`build` проверяет типы и создаёт `frontend/dist/`. `preview` по умолчанию доступен на `http://localhost:4173`, требует готовую сборку и также использует бэкенд на `127.0.0.1:8000`. Это локальная проверка сборки, не production-сервер. Неизвестные клиентские URL отображают страницу «Страница не найдена» со ссылкой домой; dev/preview возвращают SPA-оболочку и при прямом открытии вложенного URL.

### Требования production-хостинга

- Статические файлы берутся из `frontend/dist/`.
- `/health` маршрутизируется в бэкенд **до** SPA fallback, с сохранением статуса и тела ответа. Не отдавать на этот путь `index.html`.
- До SPA fallback маршрутизируются API-пути `/auth/*`, `/admin/*`, `/invitations/*`, `/account/*`, `/conversations`, `/conversations/*`, `/messages/*`, `/tags`, `/tags/*`. Иначе фронтенд получит HTML вместо JSON.
- Клиентские URL должны возвращать `index.html` при прямом открытии и обновлении страницы; существующие assets раздаются как файлы, отсутствующие assets должны давать `404`.
- Браузер и API используют один origin; CORS не настроен, Vite proxy в production отсутствует. Конкретный хостинг и reverse proxy ещё не выбраны.
- Переменные `VITE_*` попадают в публичную сборку: секреты туда не помещать. Vite автоматически читает frontend env-файлы; `.env.local` и `.env.*.local` игнорируются git, но это не защищает значения от включения в bundle. Python-бэкенд `.env` автоматически не читает.

## Как начинать задачу

1. Найти историю в индексе, прочитать её критерии и зависимости.
2. Сверить её с актуальным issue и комментариями в GitHub. Локальная копия — снимок, а не гарантия актуальности.
3. Прочитать относящиеся к задаче правила, ADR и открытые вопросы. Остальную базу знаний не загружать.
4. Если задача зависит от макета — открыть вложения истории и выяснить актуальную версию до реализации.
5. Реализовать полный сценарий и проверить его критерии. Исходные stories не переписывать ради плана или отчёта.
