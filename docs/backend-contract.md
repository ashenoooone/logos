# Контракт бэкенда

Документ описывает реализованное HTTP-поведение сервиса на текущей ветке. Сервис — FastAPI-приложение `logos_backend.app:app`; источник продуктовых решений #10 — ADR-0008.

Реализованы email-OTP для входа менеджеров, парольный вход администратора, приглашения, профиль, каналы, входящие, сортировка и теги. Проверки описывает главный агент; этот документ не утверждает, что они пройдены.


## Общие свойства HTTP

- Префикса версии и общего `/api` нет.
- Документация отключена: `GET /docs`, `GET /redoc`, `GET /openapi.json` возвращают `404` с телом `{"detail":"Not Found"}`.
- Неизвестный путь — `404` `{"detail":"Not Found"}`; неподдерживаемый метод для существующего пути — `405` `{"detail":"Method Not Allowed"}` с заголовком `Allow`. Это стандартное поведение фреймворка.
- Успешные ответы и прикладные ошибки — `application/json`. Единственное исключение — превышение размера тела: `413` с `text/plain` и телом `Content Too Large`.
- Тело любого запроса ограничено **16 КиБ**, кроме загрузки файла ответа `POST /conversations/{id}/files` — **20 МиБ**. Превышение отклоняется до разбора тела и до записи в БД.
- Ошибка разбора тела и ограничений полей — `422 {"detail": "<безопасное описание>", "field": "<имя поля>"}`. Исходные `password`, `token` и `input` не возвращаются. Для прикладных ошибок форма та же.
- CORS не настроен: заголовков `Access-Control-Allow-*` нет. Браузерный фронтенд должен работать на том же origin, что и API.
- Ответы, содержащие субъекта, CSRF-токен или состояние ссылки, имеют `Cache-Control: no-store`.

## Сессии, cookie и CSRF

### Cookie сессии

- Имя — `logos_session`; значение — случайный opaque-токен. В БД хранится только SHA-256-дайджест.
- Атрибуты: `HttpOnly`, `SameSite=Lax`, `Path=/`; `Secure` выставляется только когда запрос пришёл по `https`.
- `Max-Age` 30 дней выставляется только при `remember=true`. Без него cookie является сессионной (до закрытия браузера), но серверный срок всё равно 30 дней.
- Выход и любой успешный вход отзывают прежнюю сессию из cookie и выдают новую.
- Ограничение браузеров: сессионная cookie может пережить закрытие браузера, если он восстанавливает сессию. Сервер не может это достоверно определить; более строгая гарантия не обещается.

### CSRF

- Bootstrap: `GET /auth/csrf` → `200 {"csrf_token":"..."}` и cookie `logos_csrf` (без `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` под HTTPS). Повторный вызов сохраняет действующий токен.
- Каждый небезопасный запрос (`POST`) требует одновременно:
  - заголовок `Origin`, канонически равный origin запроса (схема + host) или одному из значений `LOGOS_ALLOWED_ORIGINS`;
  - заголовок `X-CSRF-Token`, точно совпадающий с cookie `logos_csrf`.
- Иначе — `403`: `{"detail":"Request origin is not allowed"}` или `{"detail":"CSRF verification failed"}`.
- Это относится и к анонимным запросам: OTP-запрос/проверка, вход администратора и принятие приглашения требуют предварительного `GET /auth/csrf`.
- `LOGOS_ALLOWED_ORIGINS` — только список разрешённых Origin для этой проверки. Он **не** включает CORS и **не** влияет на атрибут `Secure` cookie.

### HTTPS за reverse proxy

`Secure` вычисляется из схемы запроса, которую видит Uvicorn. Если TLS завершается на reverse proxy, Uvicorn нужно явно запустить с доверием к заголовкам прокси, например:

```sh
uv run uvicorn logos_backend.app:app --host 127.0.0.1 --port 8000 --workers 1 \
  --proxy-headers --forwarded-allow-ips 127.0.0.1
```

`--forwarded-allow-ips` должен содержать только адрес доверенного прокси, а не `*`. Без этого схема останется `http`, и `Secure` не будет выставлен. Настройки `LOGOS_ALLOWED_ORIGINS` для этого недостаточно.

## Вход и текущий субъект

### `POST /auth/admin/login`

Требует CSRF. Тело: `{"login": string, "password": string, "remember"?: boolean}`. `login` сравнивается с CLI-логином точно, без нормализации; политика сложности к паролю не применяется. Лимиты полей: `login` и `password` — 1024 символа.

Успех — `200 {"subject":{"type":"administrator"}}` и cookie сессии. В ответе **нет** `login` и имени: фронтенд должен подписать администратора сам (известная проблема для фронтенд-этапа).

### `POST /auth/manager/otp/request`

Требует CSRF. Тело: `{"email": string}` (до 254 символов). Email обрезается по краям и сравнивается через Unicode casefold; активным считается только менеджер с уже заданным паролем (приглашение принято). Сгенерированный код — 6 криптографически случайных цифр, действует 600 секунд, допускает 5 проверок. Повтор разрешён через 60 секунд и немедленно заменяет прежний код.

| Условие | Код | Тело |
|---|---|---|
| Запрос принят | `202` | `{"detail":"If the account exists, a sign-in code will be sent"}` |
| Некорректный email | `422` | `{"detail":"Invalid email address","field":"email"}` |
| Повтор в окне 60 секунд | `429` | `{"detail":"Too many code requests","retry_after_seconds":N}` + `Retry-After` |
| SMTP недоступен | `503` | `{"detail":"Email delivery is temporarily unavailable"}` |

Для активного менеджера код сохраняется в БД только как Argon2id-хеш; неизвестному и ожидающему приглашения адресу отправляется такой же по формату случайный шестизначный decoy, который не сохраняется и не может пройти проверку. Письмо или нейтральный ответ не подтверждают наличие регистрации. Для всех валидных адресов используется один и тот же путь отправки SMTP и нейтральное тело ответа, а 60-секундное окно учитывается одинаково.

До изменения кода и окна запроса проверяется доступность SMTP; ошибка проверки возвращает общий `503` независимо от существования аккаунта и не меняет прежний код. Ошибка фактической отправки также возвращает тот же `503` для активного, неизвестного и ожидающего адреса; к этому моменту окно запроса уже занято, а код активного менеджера заменён. SMTP-ошибки не журналируются с адресом или кодом.

### `POST /auth/manager/otp/verify`

Требует CSRF. Тело: `{"email":string,"code":string (ровно 6 цифр),"remember"?:boolean}`. Email нормализуется так же, как при запросе.

Успех — `200 {"subject":{"type":"manager","id":number,"name":string,"email":string}}` и cookie сессии; `remember=true` включает Max-Age 30 дней. Истёкший, неверный, использованный, заменённый или исчерпавший 5 попыток код даёт `401 {"detail":"Invalid or expired sign-in code"}`. Повторное использование не создаёт сессию. Тело кода не отражается в ответах.

Ошибки администратора: неверные данные `401 {"detail":"Invalid credentials","attempts_remaining":N}`; после пяти неудач `423 {"detail":"Too many login attempts","attempts_remaining":0,"retry_after_seconds":N}` + `Retry-After`. Блокировка длится 15 минут. Ошибка поля — `422 {"detail","field"}`; тело больше 16 КиБ — `413 Content Too Large`.

### `GET /auth/me`

Без тела. Действующая сессия — `200 {"subject": ...}` (форма как у входа). Нет или истекла — `401 {"detail":"Unauthorized"}`.

### `POST /auth/logout`

Требует CSRF. Отзывает сессию из cookie, если она есть, и удаляет cookie. Ответ — `204` без тела; повторный вызов тоже `204`.

## Административные операции с менеджерами

Все три операции требуют действующую сессию администратора и CSRF.

- Нет сессии — `401 {"detail":"Unauthorized"}`.
- Сессия менеджера — `403 {"detail":"Forbidden"}`.
- Роль берётся из сессии; поле роли в теле не читается и игнорируется.

### `GET /admin/managers`

`200 {"managers":[{"id","name","email","role":"manager","status":"pending"|"active","created_at":"<ISO-8601 UTC>"}]}` в порядке создания. Администратор в список не входит.

### `POST /admin/managers`

Тело: `{"name": string, "email": string}`. Имя обязательно, обрезается и не может быть пустым (до 200 символов). Email проверяется по синтаксису, обрезается и нормализуется без учёта регистра (до 254 символов); точки и `+`-алиасы не объединяются. Создаётся только роль «менеджер»; на email отправляется приглашение.

| Условие | Код | Тело |
|---|---|---|
| Создано и письмо передано SMTP | `201` | `{"manager":..., "delivery":{"status":"sent"}}` |
| Пустое имя | `422` | `{"detail","field":"name"}` |
| Некорректный или занятый email | `422` | `{"detail","field":"email"}`, запись не создаётся |
| SMTP недоступен/настроен неверно | `502` | `{"detail":"Invitation email could not be delivered","manager":..., "delivery":{"status":"failed"}}` |

При `502` ожидающий менеджер и его ссылка сохранены; повторная отправка выполняется тем же `POST /admin/managers/{id}/invitation`.

### `POST /admin/managers/{id}/invitation`

Тело: `{"email"?: string}` (до 254 символов). Исправляет email только ожидающего менеджера и/или выпускает новую ссылку. Предыдущая действующая ссылка приглашения отзывается. Активному менеджеру операция недоступна.

| Условие | Код | Тело |
|---|---|---|
| Успех | `200` | `{"manager":..., "delivery":{"status":"sent"}}` |
| Нет менеджера | `404` | `{"detail":"Manager not found"}` |
| Пароль уже задан | `409` | `{"detail":"Manager has already accepted the invitation"}` |
| Некорректный/занятый email | `422` | `{"detail","field":"email"}` |
| SMTP-сбой | `502` | как выше; новый email и ссылка сохранены |

## Приглашение и установка пароля

Ссылка из письма ведёт на фронтенд-страницу `/invitation#token=<urlencoded>`. Токен передаётся только во фрагменте URL; API принимает его только в JSON-теле POST. В путях, query, ответах и письмах-логах токена нет.

- `POST /invitations/preview` — CSRF; тело `{"token"}`. `200 {"name","email","expires_at"}` (email неизменяем, берётся из БД). Использованная, отозванная, просроченная или неизвестная ссылка — `410 {"detail":"Invitation is no longer valid"}`.
- `POST /invitations/accept` — CSRF; тело `{"token","password","password_confirmation"}`. Проверяет политику и точное совпадение повтора. Ошибка пароля — `422 {"detail","field":"password"}`, ссылка остаётся действующей. Успех — `200 {"subject":...}` и новая cookie сессии; в одной транзакции ссылка гасится, менеджер активируется, создаётся сессия. Недействительная ссылка — `410` без изменения пароля и без сессии.
- Политика пароля установки и смены: минимум 8 символов, хотя бы одна буква любого алфавита и одна десятичная цифра. Пробелы не обрезаются, пароль не нормализуется, повтор обязан совпадать точно.
- Ссылка действует ровно 72 часа: при `now == expires_at` она уже недействительна. В БД только SHA-256-дайджест. При двух конкурентных принятиях успешно не более одного.

## Удалённые маршруты

Больше не зарегистрированы: `POST /auth/manager/login`, `POST /password-reset/request`, `POST /password-reset/preview`, `POST /password-reset/complete`. Менеджер входит только по email-коду; пароль нужен для принятия приглашения и смены в профиле. Восстановления пароля нет.

## Профиль менеджера

Все `POST /account/*` требуют CSRF. `name`, `email`, `password` — только сессия менеджера (`401` без сессии, `403` администратору). Ошибки полей — `422 {"detail","field"}`.

| Эндпоинт | Тело | Успех | Ошибки |
|---|---|---|---|
| `POST /account/name` | `{"name"}` (≤200) | `200 {"subject"}` | `422 field=name` — пустое имя |
| `POST /account/email` | `{"email"}` | `202 {"pending_email"}`; письмо на новый адрес | `422 field=email`: `Invalid email address`, `Email is unchanged`, `Email is already taken`; `502` — SMTP не принял письмо |
| `POST /account/email/confirm` | `{"token"}`; без сессии | `200 {"manager_id","email"}` | `410` — ссылка использована, заменена или просрочена; `409` — адрес заняли до подтверждения |
| `POST /account/password` | `{"current_password","new_password","new_password_confirmation","sign_out_other_devices":true}` | `200 {}` | `422 field=current_password` (не указан или неверен), `field=new_password_confirmation` (не совпал), `field=new_password` (политика пароля) |

- Смена email: ссылка `/email-confirmation#token=…`, одноразовая, 24 часа; новый запрос заменяет прежнюю. До подтверждения вход по старому email. Сессии не отзываются, старый адрес не уведомляется (ADR-0007).
- Смена пароля: текущий пароль подтверждает владельца профиля. Его ошибка не блокирует вход по OTP. С `sign_out_other_devices` удаляются все сессии менеджера, кроме текущей.

## Каналы (Telegram)

Только администратор (`401` без сессии, `403` менеджеру); все `POST` требуют CSRF. Один бот на установку, получение обновлений — long polling (ADR-0007). Токен в ответах не возвращается никогда.

| Эндпоинт | Тело | Успех | Ошибки |
|---|---|---|---|
| `GET /admin/channels` | — | `200 {"channel":{"provider":"telegram","name","bot_username","status","error","updated_at"}}`; ни разу не подключали — `status=disconnected`, остальное `null` | — |
| `POST /admin/channels/telegram/check` | `{"token"}` (≤200) | `200 {"bot_username"}`; ничего не сохраняет | `422 field=token` — `Invalid bot token`; `502` — Bot API недоступен |
| `POST /admin/channels/telegram` | `{"token","name"?}` (≤200; пустое имя → `Telegram`) | `200 {"channel"}`, `status=connected` | `422 field=token`; `409` — уже подключён; `502` |
| `POST /admin/channels/telegram/disconnect` | — | `200 {"channel"}`, `status=disconnected` | `404` — канала нет |

- Токен проверяется форматом `<id>:<секрет>` до запроса и `getMe` в Bot API (`401`/`404` → неверный). Неверный токен канал не меняет.
- Подключение вызывает `deleteWebhook(drop_pending_updates)`: накопленные до подключения сообщения не забираются.
- Фоновый поток (lifespan приложения) вызывает `getUpdates` с таймаутом 25 с. `401`/`404` → `status=error`, `error=token_invalid`; `409` (обновления забирает другое приложение) → `error=conflict`. Опрос канала в `error` останавливается до переподключения тем же `POST /admin/channels/telegram`. Сетевые сбои статус не меняют — повтор через 5 с. Сообщения сохраняются (см. «Входящие») до сдвига `update_offset`.
- Отключение стирает токен, строку канала оставляет.

## Входящие (#6)

Только менеджер (`401` без сессии, `403` администратору); все `POST`/`PUT`/`DELETE` требуют CSRF. Источник решений — ADR-0007.

| Эндпоинт | Тело | Успех | Ошибки |
|---|---|---|---|
| `GET /conversations` | optional `?q=<string>` (подстрока без учёта регистра в имени клиента или тексте сообщений) | `200 {"conversations":[{"id","provider":"telegram","name","last_message_at","unread_count","last_message","tags":[{"id","name"}]}],"unread_total","last_incoming_id","incoming_total"}`; новые сверху | — |
| `GET /conversations/{id}/messages` | — | `200 {"conversation":{"id","provider","name","tags"},"messages":[…]}`; вся переписка по порядку | `404` |
| `POST /conversations/{id}/read` | — | `200 {"status":"ok"}`; входящие диалога прочитаны для всех менеджеров | `404` |
| `POST /conversations/{id}/messages` | `{"text"}` (1–4096 после trim) | `200 {"message"}`, `status` = `delivered`/`failed` | `422 field=text`; `404` |
| `POST /conversations/{id}/files?name=&text=` | сырое тело файла, 1 Б–20 МиБ; `name` ≤255, `text` ≤1024 | `200 {"message"}` — отправка `sendDocument` | `422 field=file`/`name`/`text`; `413`; `404` |
| `POST /messages/{id}/retry` | — | `200 {"message"}` | `409` — ответ не в статусе `failed` |
| `GET /messages/{id}/attachment` | — | файл: фото — `image/jpeg` inline, документ — `application/octet-stream` attachment; `nosniff`, `CSP: sandbox` | `404` |

`message`: `{"id","direction":"in"|"out","author":string|null,"kind":"text"|"photo"|"document"|"unsupported","text","file":{"name","size","available"}|null,"status":null|"sending"|"delivered"|"failed","created_at"}`.
## Сортировка и фильтры (#7)

Только менеджер; у каждого свои настройки. Сортировка и фильтрация выполняются на фронтенде по полному `GET /conversations`; сервер хранит выбор.

| Эндпоинт | Тело | Успех | Ошибки |
|---|---|---|---|
| `GET /conversations/preferences` | — | `200 {"sort":"newest"/"oldest"/"unread","saved_filters":[{"id","name","filters"}]}`; по умолчанию `newest` | — |
| `PUT /conversations/preferences/sort` | `{"sort"}` | `200` — как `GET` | `422 field=sort` |
| `POST /conversations/saved-filters` | `{"name"` (1–50 после trim)`,"filters":{"channel":["telegram"],"tag":[id],"status":["unread"/"read"]}}` | `200` — как `GET`; то же название перезаписывает набор | `422` |
| `DELETE /conversations/saved-filters/{id}` | — | `200` — как `GET`; чужой/несуществующий id игнорируется | — |

Значения внутри фильтра — ИЛИ, разные фильтры — И (ADR-0007).

## Теги (#8)

Имя 1–50 символов после trim, уникально без учёта регистра (`casefold`). Удаление тега снимает его со всех диалогов.

| Эндпоинт | Кто | Тело | Успех | Ошибки |
|---|---|---|---|---|
| `GET /tags` | менеджер | — | `200 {"tags":[{"id","name","standard","own","author","conversation_count"}]}` | — |
| `POST /conversations/{id}/tags` | менеджер | ровно одно из `{"tag_id":<number>}` (существующий видимый стандартный/свой тег) или `{"name":"..."}` (явно создать тег менеджера) | `200 {"tags":[{"id","name"}]}` | `422` оба поля/ни одного или invalid `name`; `403` невидимый чужой тег; `404` неизвестный `tag_id` или диалог; `409` имя уже занято при явном создании |
| `DELETE /conversations/{id}/tags/{tag_id}` | менеджер | — | `200 {"tags"}` — тег снят с диалога | `404` |
| `DELETE /tags/{id}` | менеджер | — | `200` — только свой тег | `403` чужой/стандартный; `404` |
| `GET /admin/tags` | администратор | — | `200 {"tags"}` | — |
| `POST /admin/tags` | администратор | `{"name"}` | `200 {"tags"}` — стандартный тег | `409` имя занято; `422` |
| `PATCH /admin/tags/{id}` | администратор | `{"name"}` | `200 {"tags"}` — любой тег | `409`; `422`; `404` |
| `DELETE /admin/tags/{id}` | администратор | — | `200 {"tags"}` — любой тег | `404` |

| `0006` | `conversations`, `messages` + индексы `ix_messages_conversation`, частичный уникальный `uq_messages_incoming` |
| `0007` | `tags`, `conversation_tags`, `inbox_preferences`, `saved_filters` |
| `0008` | без схемы: при `LOGOS_DEV_ADMIN=1` и пустой `administrators` создаёт тестового администратора `admin`/`admin`; без переменной ничего не делает. Только для локальной разработки |
| `0009` | без схемы: при `LOGOS_DEMO_SEED=1` и пустой базе (нет менеджеров и диалогов) — демо-данные из `demo_seed.py`: 3 менеджера `*@demo.logos` / `demo1234`, теги, 7 фейковых диалогов Telegram (непрочитанные, документ, «Не доставлено»), сохранённый фильтр; подключает демо-бота только при заданном `LOGOS_DEMO_BOT_TOKEN` (в коде токена нет; без токена или Bot API — без бота). Ответы в демо-диалоги уходят в «Не доставлено». Не для production |
| `0010` | `manager_otp_codes`, `manager_otp_requests`, `messages.manager_id`; удаляет старые `/start`-сообщения без удаления переписки |

- `administrators` (`id=1`, `login`, `password_hash`): единственный администратор, создаётся CLI; миграция `0002` не меняет строку и её логин/хеш.
- `managers`: уникальный `email_normalized` на уровне БД; `password_hash` пуст у ожидающего; ограничения непустых имени/email.
- `sessions`: уникальный `token_hash`, ровно один владелец (администратор или менеджер), `expires_at > created_at`.
- `one_time_links`: уникальный `token_hash`, purpose (`invitation`/legacy `password_reset`), `consumed_at`/`revoked_at`, срок действия и частичный уникальный индекс для одной активной ссылки на менеджера. Ссылки восстановления больше не выпускаются и не проверяются.
- `email_changes`: одна неподтверждённая смена на менеджера (уникальный `manager_id`), уникальный `token_hash`, новый адрес и его нормализованная форма; подтверждение удаляет строку.
- `channels`: одна строка (`id=1`), `status` ∈ `connected`/`error`/`disconnected`, код ошибки, токен **открытым текстом** (ADR-0007; `NULL` после отключения), `update_offset` для `getUpdates`, `connected_at` отличает переподключения от устаревших результатов опроса.
- `conversations`: диалог = личный чат Telegram, уникальный `chat_id`, имя клиента, `last_message_at`.
- `messages`: `direction` `in`/`out`, `kind`, текст/подпись, имя/размер файла, `file_path` — имя файла в `attachments/` рядом с SQLite (отдаётся только через API). У входящих `read_at` (общая прочитанность), у исходящих `status`. Частичный уникальный индекс `(conversation_id, telegram_message_id) WHERE direction='in'` отсекает дубли.
- `tags`: уникальный `name_normalized`; `manager_id` NULL — стандартный тег, иначе автор. `conversation_tags` — связь с CASCADE на диалог и тег.
- `inbox_preferences` (`manager_id`, `sort`) и `saved_filters` (`manager_id`, `name` уникально у менеджера, `filters` — JSON).
- `manager_otp_codes`: один хеш кода, срок действия, счётчик попыток и время выдачи на активного менеджера; неверные попытки сохраняются.
- `manager_otp_requests`: последний разрешённый запрос на нормализованный email для общего 60-секундного ограничения.

В БД не хранятся открытые токены сессий и одноразовых ссылок — только SHA-256-дайджесты. Исключение — токен Telegram-бота: он нужен для вызовов Bot API.

## Конфигурация

Все значения читаются из окружения процесса. `.env` автоматически **не** загружается; переменные нужно экспортировать.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LOGOS_DATABASE_PATH` | путь к SQLite; пустое значение = не задано | `data/logos.sqlite3` от каталога запуска |
| `LOGOS_ALLOWED_ORIGINS` | дополнительные разрешённые Origin через запятую; `*` не поддерживается | только same-origin |
| `LOGOS_PUBLIC_BASE_URL` | базовый адрес фронтенда для ссылок в письмах | `http://localhost:5173` |
| `LOGOS_SMTP_HOST` | SMTP-сервер | `127.0.0.1` |
| `LOGOS_SMTP_PORT` | SMTP-порт (целое) | `1026` |
| `LOGOS_SMTP_FROM` | отправитель | `no-reply@logos.local` |
| `LOGOS_SMTP_USERNAME` | логин SMTP, если нужен | не задан |
| `LOGOS_SMTP_PASSWORD` | пароль SMTP, если нужен | не задан |
| `LOGOS_SMTP_TLS` | `none`/`starttls`/`ssl` | `none` |
| `LOGOS_SMTP_TIMEOUT` | таймаут SMTP-соединения, секунды | `10` |

Неверные SMTP-порт, таймаут или режим TLS не дают `500`: приглашение возвращает `502`, запрос менеджерского кода — `503`.

SMTP-пароль и токены не должны попадать в `VITE_*`, CLI-аргументы, логи или ответы API. Локальный Mailpit (`docker-compose.yml`, SMTP `127.0.0.1:1026`, UI `127.0.0.1:8026`) — перехватчик писем, а не внешняя доставка. Очередь, фоновые повторы и Redis не используются: выполняется ровно одна SMTP-попытка на запрос.

## `GET /health`

Без тела и авторизации.

| Условие | Код | Тело |
|---|---|---|
| SQLite доступна, все таблицы миграций присутствуют | `200` | `{"status":"ok"}` |
| Файл/каталог недоступен, таблицы нет, колонок `administrators` не хватает | `503` | `{"detail":"Database is not ready"}` |

Это проверка наличия схемы, а не версии миграций, целостности данных или наличия администратора. Внешние интеграции (SMTP, Telegram) не проверяются.

## Консольная команда (не HTTP)

`uv run logos-backend create-admin --login <login>` — операция развёртывания.

- Требует TTY; иначе код `1` без запроса пароля. Пароль вводится скрыто дважды; пустой, несовпадение или отмена — код `1`. Требований сложности нет.
- Логин обязателен, не пустой и не из пробелов, сохраняется точно. Других полей нет.
- Сохраняется только Argon2id-хеш. При существующем администраторе код `1`, запись не меняется. Неверные аргументы — код `2`.
- После создания администратор входит через `POST /auth/admin/login` тем же логином и паролем.

## Развёртывание и reverse proxy

- Браузер и API должны быть на одном origin; CORS не настроен.
- Reverse proxy маршрутизирует в бэкенд **до** SPA fallback как минимум `/health`, `/auth/*`, `/admin/*`, `/invitations/*`, `/account/*`, `/conversations*`, `/messages/*`, `/tags*`, сохраняя статус и тело ответа. Остальные пути могут отдавать `index.html`.
- При завершении TLS на прокси Uvicorn запускается с явными `--proxy-headers --forwarded-allow-ips <доверенный прокси>`, иначе `Secure` cookie не выставится.
- Vite dev/preview проксирует `/health`, `/auth`, `/admin`, `/invitations`, `/account`, `/conversations`, `/messages`, `/tags`. SPA-маршруты не начинаются с этих префиксов. Vite не является production-сервером.

## Что заведомо не реализовано

- Публичная саморегистрация и отключение менеджеров.
- Восстановление пароля (для менеджеров и администратора).
- CORS, метрики, трассировка, health-проверки внешних сервисов и OpenAPI.
- Постраничность переписки и WebSocket/SSE.
- Типы сообщений Telegram кроме текста, фото и документов (показываются как неподдерживаемые); группы и каналы Telegram.

Любой другой путь или метод, кроме описанных здесь, не является частью контракта, даже если фреймворк отвечает на него стандартной ошибкой.
