# Контракт бэкенда

Документ описывает **реализованное сейчас** поведение сервиса на ветке `feat/backend-initialization`. Источник решений — [ADR-0002](adr/0002-backend-initialization.md); команды установки и запуска — в [README](../README.md).

Сервис — FastAPI-приложение `logos_backend.app:app`. Пока реализованы только проверка готовности БД и консольная команда создания первого администратора. Регистрация, вход, сессии, административный API, каналы и переписка отсутствуют.

## Общие свойства HTTP

- Префикса версии и общего `/api` нет.
- Аутентификации, cookie, CORS, CSRF и rate limiting нет.
- Документация отключена: `GET /docs`, `GET /redoc`, `GET /openapi.json` возвращают `404` с телом `{"detail":"Not Found"}`.
- Неизвестный путь возвращает `404` с телом `{"detail":"Not Found"}`; неподдерживаемый метод для существующего пути — `405` с телом `{"detail":"Method Not Allowed"}` и заголовком `Allow` со списком разрешённых методов. Оба ответа — стандартное поведение фреймворка, а не собственные обработчики.
- Успешные ответы и ошибки имеют тип `application/json`.

## `GET /health`

Единственный прикладной эндпоинт. Параметров, тела запроса и авторизации нет.

| Условие | Код | Тело |
|---|---|---|
| SQLite доступна, таблица `administrators` содержит колонки `id`, `login`, `password_hash` | `200` | `{"status":"ok"}` |
| Файл или каталог БД отсутствует/недоступен, таблицы нет, колонок не хватает | `503` | `{"detail":"Database is not ready"}` |

Границы проверки:

- Это проверка **наличия схемы**, а не версии миграций, целостности данных или наличия строки администратора. Мигрированная БД без администратора считается готовой.
- `503` возвращается и при ошибке соединения с SQLite.
- Проверка выполняется на каждый запрос; соединение с БД не кешируется между запросами.
- Эндпоинт не подтверждает работоспособность внешних интеграций — их ещё нет.

`POST /health` и другие методы дают `405` (см. выше).

## Схема данных

Единственная прикладная таблица — `administrators`, создаётся миграцией `0001`:

| Колонка | Тип SQLite | Ограничения |
|---|---|---|
| `id` | `INTEGER` | первичный ключ, `CHECK (id = 1)` |
| `login` | `TEXT` | `NOT NULL`, хранится без нормализации |
| `password_hash` | `TEXT` | `NOT NULL`, Argon2id-хеш |

Ограничение `id = 1` делает администратора единственным на уровне БД, включая конкурирующие вставки.

## Конфигурация

- `LOGOS_DATABASE_PATH` — путь к файлу SQLite. Значение по умолчанию — `data/logos.sqlite3` относительно текущего каталога процесса. Относительный путь разрешается от каталога запуска, поэтому для развёртывания рекомендуется абсолютный. Пустое значение или только пробелы трактуются как отсутствие переменной.
- `.env` автоматически не читается; переменную нужно экспортировать в окружение.
- Миграции применяются только явно: `uv run alembic upgrade head`. Приложение не создаёт и не обновляет схему при старте.

## Консольная команда (не HTTP)

Точка входа `logos-backend`, подкоманда `create-admin --login TEXT`. Это операция развёртывания, не API, и она не доступна по сети.

Поведение:

1. Требуется TTY на stdin; иначе ошибка и код `1` без запроса пароля. Если терминал не позволяет отключить эхо, команда также завершается с кодом `1`, не читая пароль.
2. Пароль запрашивается дважды скрытым вводом. Пустой пароль, несовпадение или отмена ввода (`EOF`, `Ctrl+C`) — ошибка и код `1`. Требований сложности нет.
3. Пароль хешируется Argon2id с параметрами библиотеки по умолчанию; хеш — единственное, что сохраняется.
4. Вставка выполняется с `id = 1` в одной транзакции. Если администратор уже существует, возвращается ошибка и код `1`; существующие логин и хеш не меняются при любом переданном логине.
5. Если БД не мигрирована или недоступна — код `1` с подсказкой выполнить `alembic upgrade head`.
6. Неверные аргументы (отсутствующий, пустой или пробельный логин) — код `2` от argparse.

Коды: `0` — администратор создан; `1` — уже существует, БД не готова, ошибка ввода, хеширования или хранения; `2` — ошибка аргументов.

Пароль запрашивается до проверки существующего администратора; авторитетна вставка в БД. Повторный запуск поэтому всегда требует ввода пароля, даже когда создание заведомо не произойдёт.

Техническая учётная запись не даёт входа в приложение: механизма аутентификации нет.

## Что заведомо не реализовано

- Вход, сессии, выход, восстановление пароля, приглашения.
- Регистрация менеджеров и любые поля профиля.
- Административные HTTP-эндпоинты, управление каналами, отправка и получение сообщений.
- Фронтенд, CORS для него, загрузка и раздача вложений.
- Health-проверки внешних сервисов, метрики, трассировка.

Любой другой путь или метод, кроме описанных здесь, не является частью контракта, даже если фреймворк отвечает на него стандартной ошибкой.
