# ADR-0006: первый сценарий приглашения и входа

- Дата: 2026-11-04.
- Статус: **принято пользователем**. Правила ниже согласованы до продуктового кода.
- Основание: ответы пользователя при выполнении [#9](https://github.com/ashenoooone/logos/issues/9).

## Context

#9 требует подготовки требований, затем отдельных backend- и frontend-этапов для #1–#3 с явным объёмом зависимости от #4. Все восемь вложений #1–#4 открыты; поздние макеты расходятся с исходными и текстом #1 в части выбора роли. Существующий администратор имеет произвольный CLI `login`, не email.

## Decision

### Приоритет макетов и объём

- **Решили:** дополнительные `image.png` имеют приоритет; список сотрудников берётся из исходного LOG-33.png. Форма добавления содержит обязательные имя и фамилию одним полем и email; роль фиксирована «Менеджер», приглашение отправляется обязательно. Выбор роли из текста #1 явно отменён этим согласованным решением; исходный снимок истории не переписывается.
- **Почему:** пользователь выбрал «Поздние макеты + восстановление» после предъявления конфликта.
- **Отвергли:** приоритет исходных LOG-*.png; добавление отключения сотрудников; включение всей #4 в первый сценарий.
- **Решили:** реализовать #1–#3 и рабочее восстановление пароля из #4: одноразовая ссылка на 1 час, повторный запрос не чаще раза в 60 секунд и подсказка о папке «Спам». Смена email, профиль и смена пароля с текущим паролем остаются вне первого инкремента.
- **Почему:** восстановление уже требуется #3; неработающая ссылка не удовлетворяет этому требованию.
- **Отвергли:** ссылку-заглушку и молчаливое исключение восстановления.

### Вход администратора

- **Решили:** отдельный веб-вход администратора по существующему CLI `login` и паролю. Существующие идентификатор и хеш сохраняются; менеджеры входят по email. Администратор получает также пользовательские права; раздел «Сотрудники» доступен только ему.
- **Почему:** пользователь выбрал «Отдельный вход по CLI login»; это не требует трактовать произвольный технический login как email.
- **Отвергли:** принудительное назначение email существующему администратору, публичную регистрацию администратора и ограничение его только административными правами.

### Локальная доставка писем

- **Решили:** по явному запросу пользователя сначала использовать локальный перехват писем как в `/Users/romangontar/Desktop/projects/remo-site`: настоящий SMTP-транспорт приложения и Mailpit вместо доставки во внешние почтовые ящики. Не подменять отправку записью ссылки в лог или фиктивным успешным ответом.
- **Почему:** пользователь запросил «моковую отправку» по этому образцу. В образце проверены `apps/api/src/infrastructure/mail/smtp-mail.sender.ts` (SMTP) и `docker-compose.yml` (Mailpit `axllent/mailpit:v1.27`, SMTP 1025, интерфейс 8025). Redis и очередь из другого проекта этим решением не заимствуются.
- **Отвергли:** выбор внешнего почтового провайдера как предварительное условие локального инкремента; fake-success без полученного письма.
- Это **согласованное сокращение объёма** относительно требования #9 о реальной внешней доставке. Получение письма в Mailpit не доказывает доставку менеджеру; этот критерий исходных #1/#4 и полного #9 остаётся открытым.

### Email, состояние аккаунта и пароль

- **Решили:** обрезать внешние пробелы email и сравнивать адреса без учёта регистра; уникальность действует и до задания пароля. Не объединять точки и `+`-алиасы. До задания пароля аккаунт ожидает входа и не может войти по паролю.
- **Почему:** пользователь выбрал «Email без регистра; пароль по макету»; повтор приглашения не должен создавать вторую учётную запись.
- **Отвергли:** разные аккаунты для `User@example.com` и `user@example.com`, провайдер-зависимое объединение адресов.
- **Решили:** пароль — минимум 8 символов, хотя бы одна буква любого алфавита и одна десятичная цифра. Не обрезать пробелы и не нормализовать пароль; повтор должен совпадать точно. Политика едина для установки и восстановления; существующие CLI-пароли не менять и не переоценивать при входе.
- **Почему:** согласованная трактовка одинаковых требований обеих версий #2.
- **Отвергли:** ограничение обязательной буквы/цифры только ASCII и выдуманные требования к регистру или спецсимволам.

### Блокировка входа

- **Решили:** 5 неверных попыток по идентификатору входа с любых IP блокируют вход на 15 минут. Для менеджера ключ — нормализованный email, для администратора — точный CLI login в отдельном пространстве. Неизвестные идентификаторы получают те же счётчики, общую ошибку и состояние блокировки; сброс — при успешном входе, восстановлении пароля или завершении блокировки.
- **Почему:** пользователь выбрал блокировку по идентификатору после предъявления компромисса; распределение запросов по IP не обходит лимит.
- **Отвергли:** лимит только на пару идентификатор/IP.
- **Принятый риск:** посторонний, знающий email/login, может временно заблокировать вход владельца. Это не основание отключать рабочее восстановление.

### Сессии и восстановление

- **Решили:** серверные отзывные сессии в SQLite; случайный токен в `HttpOnly`/`SameSite` cookie, `Secure` под HTTPS, CSRF-защита изменяющих запросов. В БД хранится хеш секрета сессии, не открытый токен. Обычный выход отзывает текущую сессию.
- **Почему:** пользователь согласовал предложенную схему в вопросе о сессиях; она поддерживает немедленный отзыв без хранения авторизации в localStorage.
- **Отвергли:** фиктивную клиентскую сессию и необходимость ждать истечения токена после отзыва.
- **Решили:** «Запомнить меня» выключено по умолчанию; при включении cookie и сессия действуют максимум 30 дней. Иначе cookie без `Expires`/`Max-Age`, серверный предел также 30 дней. После установки пароля — новая браузерная сессия. После восстановления отозвать все прежние сессии и сразу создать новую браузерную сессию; повторный запрос восстановления отзывает предыдущую ссылку.
- **Почему:** пользователь выбрал «Отозвать все; сразу войти заново»; новая сессия не наследует неизвестное предпочтение старой.
- **Отвергли:** отдельный обязательный вход после восстановления и сохранение прежних сессий.
- **Ограничение браузеров:** восстановление закрытого браузера может сохранять session cookies. Сервер не может достоверно определить закрытие браузера; не обещать более строгой гарантии.

### Исправление приглашения и ошибки SMTP

- **Решили:** исправление email и повтор приглашения разрешены только до задания пароля, в том числе после истечения прежнего приглашения. Новая ссылка отзывает старую; каждое приглашение одноразовое и действует 72 часа.
- **Почему:** пользователь согласовал узкое действие исправления приглашения без общего редактирования активных менеджеров.
- **Отвергли:** изменение email активного менеджера через переотправку приглашения и сохранение старой действующей ссылки.
- **Решили:** при сбое SMTP сохранять ожидающего менеджера, показывать администратору ошибку доставки и разрешать повтор; не сообщать об успешной отправке. При восстановлении ответы одинаковы для известных и неизвестных email; при недоступном SMTP — общая ошибка для обоих.
- **Почему:** пользователь выбрал «Сохранять ожидающего; показать ошибку». SMTP и SQLite не составляют атомарной транзакции; сохранённое состояние позволяет явно повторить операцию.
- **Отвергли:** откат создания менеджера при ошибке SMTP и успешный ответ без отправки.

## Consequences

- Ручную приёмку технического фронтенда пользователь подтвердил ответом «Всё проверено, замечаний нет»: desktop/390 px, загрузка/повтор, 502/503/offline и восстановление, not-found/refresh, console. Это пользовательское подтверждение, не агентская браузерная проверка и не приёмка ещё не реализованных продуктовых экранов.
- Backend и frontend выполняются отдельными этапами и сессиями по фактическому контракту; #9 и полные UI-истории не закрываются по одному backend.
- Внешняя почтовая доставка и последующая ручная приёмка продуктового сценария остаются критериями полного хендоффа.
- Остальные настройки аккаунта из #4 и внешняя почтовая доставка остаются вне согласованного локального инкремента. Это не блокеры реализации утверждённого backend-сценария.
