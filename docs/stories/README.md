## Зависимости и рекомендуемая последовательность

Это рабочая интерпретация зависимостей, **не утверждённый порядок спринта**. Номер issue сам по себе не задаёт приоритет.

1. Техническая инициализация по [ADR-0001](../adr/0001-project-baseline.md): приложение, БД, миграции, конфигурация, проверки, закрытая команда создания администратора. Детали ещё нужно выбрать.
2. **#1 + #2 + #3** — связанный сценарий приглашения, задания пароля и последующего входа. Для полной приёмки #1 недостаточно только отправить письмо. Общую политику пароля определяет #2.
3. **#4** — использует учётные записи, сессии и политику пароля из предыдущей группы. Ссылка на восстановление есть уже в #3.
4. **#5 → #6** — подключение канала позволяет принять и отправить реальные сообщения. Полная приёмка #5 включает получение сообщений из #6.
5. **#8** — требует диалоги из #6.
6. **#7** — требует список диалогов из #6; для полной фильтрации по тегу также нужны теги из #8. Нельзя объявить всю #7 завершённой до этого.

В этом порядке сначала закрывается идентификация сотрудников, затем реальная переписка, затем её организация. Бэкенд и фронтенд одной группы реализуются отдельными задачами с фактическим API-контрактом между ними.

## Как обновлять снимок

1. Перед задачей проверить состояние, тело и комментарии нужного issue:

   ```sh
   gh issue view 1 --repo ashenoooone/logos --json number,title,body,state,updatedAt,comments,url
   ```

2. При изменениях перенести тело issue в соответствующий файл **дословно**. Не редактировать исходную историю ради плана, заметок или отметок о ходе реализации.
3. Обновить дату снимка и `updatedAt` в индексе. Если появились комментарии, прочитать их и явно зафиксировать влияющие на требования уточнения отдельно от исходного тела.
4. Производные правила и решения обновлять отдельно: [бизнес-правила](../domain/rules.md), [открытые вопросы](../open-questions.md), ADR.
